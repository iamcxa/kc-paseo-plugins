## 先比較互動模型，再選方向

起點一致：幕僚長頁面已載入，使用者尚未操作，沒有換官提示；桌面／手機相同。一次點按、一次點欄、一次連續輸入、一次送出各算 1；閱讀及等待不算，捲動另計。時間與理解品質未量測。

1. 自動開場對話：進入即檢查，改變才掃描；知道建議 0，開具名目標 1。理解後的決策仍走原確認流程。
2. 手動掃描對話：按掃描 1，再開目標 1；相同可見結果多 1，且要先知道得按掃描。優點是使用者控制每次模型回合，缺點是不符進入即對齊焦點。
3. 摘要加 Replay：以已完成摘要起算讀摘要 0，Replay 1，再開 FO 1；若從尚未收集開始還需 collect now 1。摘要本身沒替艦長挑出唯一下一步。保留多點背景，但多一層理解與挑選。

選 1：少一個啟動動作，沒有新增模式，維持既有對話。選擇理由是任務的進入情境和操作數，不宣稱已證明更快。重進未變時不增加模型回合；不是一進入就無條件喚起模型。

## 排名規則與不能推論的事

1. 候選必須是未結束、未送出／轉交，且其必要來源已可確認的目前事項。權限只開具名原生會話，關卡只開具名關卡，問題開正確 FO 對話，審查保留現有去向與外部連結。來源失敗的候選不能當作已確認。
2. 第一層是已可確定某位 FO 在等艦長：權限記錄指到該代理，完整 workflowDir + slug 的正式待艦長關卡，或 next-owner=captain 的具名下一步／現有問句判定。只說「這件正等你」，不保證批准後就開工。不同層的規則是建議預設，沒有替來源增加業務重要性。
3. 第二層是 GitHub 明確向艦長發出的審查請求，但沒有可確認的 FO 等待歸屬。可說「審查請求等你；尚不能確認誰受阻」。同儲存庫、時間相近或同名任務都不足以宣稱誰被擋住。
4. 同層用事項 since 的較早有效時間先（久等先）；時間不明者後，再以完整事項 key 的固定字序決勝。沒有依據的人數、收益、工時、緊急性或跨任務依賴不參與排名。
5. FO 只是 busy／idle／new reply／error／offline 不入候選；新回覆必須已有清單問句判定，不能從狀態升級成「等艦長」。同一 FO 的關卡和另一題不能合併；同一關卡不能因關聯兩列就加兩票。
6. 目前 attachGates 會在精確匹配失敗後用同 slug 或 workflow 後備關聯；reviewOwner 會用同 repo 或文字找第一位 FO。這可作現有導覽，不是無推論的歸屬證據。排名只接受唯一的完整 workflow/task 關卡歸屬、權限原始 agentId、明確且唯一的問題來源；審查若只有 repo 對上，就顯示「相關 FO，等待歸屬未知」，不擴大成第一層或多人解阻。
7. 資料有缺口時可推薦「已確認事項中，先看這件」，同時指出缺哪個來源；全不可確認便不選，說「現在不能判定」。不能把空集合當作全艦隊無事，也不能因 source retry 失敗再次發模型回合。

這不是求證實際依賴的計畫系統。她只把「你可以做、有人明確在等」排在「只有請求、影響未知」之前；沒有聲稱全局最佳。

## 進入、版本比較、成本上限的精確意思

- 進入指首次掛載幕僚長頁，以及 Board／詳情返回其對話的 inactive→active。這些已有 client/board.tsx:589 起的 open 與 client/co-chat.tsx:326 起的 visible 邊界。單純 React 重繪、切換主題、鍵盤或相同 active 不算進入。宿主分頁／App 回前景而元件未卸載的通知，在此次來源內未驗證；不假裝有新的宿主 focus 能力。若產品實作發現滿足進入情境必須加 Paseo 能力，先回艦長，不擅改平台。
- 每次進入先讀取／比對既有來源，合成完成或明確失敗的快照；中途的 loading→loaded、輪詢查詢時間及「幾分鐘前」文字不當作內容改變。沒有輪詢驅動的模型掃描。
- 本次記憶保留最近成功掃描的事實版本及最近已嘗試版本。比較的是 FO 成員與實質狀態、next-owner／next／task／workflow、問句來源與時間、權限身份與內容、正式關卡完整身份、審查身份內容／firstSeenAt、送達／記錄狀態、來源覆蓋及失敗狀態。採完整正規化內容比較即可，不需要永久版本資料庫。
- 排除每次產生的 roundId、collectedAt、checkedAt、相對時間字串、物件順序，以及與實質 Board 狀態無關的 agent.updatedAt 變動。FO 來源時間仍保留顯示，真正的問題／權限／關卡更換及其事件時間必須進比較；若無從區分更新用途，只標未知，不能認定無變。幕僚長自己的掃描輸出、工作狀態和對話不作觸發輸入，避免自己產生新版本。
- 同版本成功不再掃；同版本失敗也不自動重試。來源恢復、實際候選變更後，下一次進入才可掃一次。重查資料的現有按鈕只做來源讀取，不等同模型 retry；使用者仍能自行在對話追問。
- 沒有候選且來源完整時直接顯示「沒有可確認待你處理的事項」，不需模型；全缺來源則顯示失敗，也不發模型。首進無記憶才對已有候選做首次掃描。
- 每次有效進入最多一個模型回合，並用本次鎖避免重複進入同時發送；忙碌就保留對話並提示暫未掃描，既不打斷也不排「忙完自動再掃」。本次掃描中途 Board 變更，完成結果標其原讀取時間及「之後已有變更」，不偷換內容或立即再掃。
- 快照和去重僅本次頁面記憶；全頁重開後重新建立，不新增跨次成本記憶、排程或恢復義務。這個限制表示頻繁重開仍可能有成本，不能承諾跨 App 啟動仍免費去重。
- 一回合可能包含多個供應商請求；本規則只限制啟動次數，不是 token、秒數或美元硬上限。若需要持久去重、背景重掃或金額上限，已超出這份方向，先回艦長。

## 開場與行動的可見結果

只說一個目標、已知的等待者／未知、等待時間及一個可走的動作。例：「先看『範例試用』關卡。範例 FO 甲這個關卡等你 42 分鐘。開關卡閱讀後決定。」等待是唯一已知影響，不說「團隊乙因此停工」。具名入口沿用現有 openItem 與事項身份，開啟前核對該身份仍可處理；若已換關卡則顯示過期，不導向同名另一件、不自動批准。

關卡完整內容、選擇、必填理由及 Confirm（確認送出）照舊；傳訊仍獨立。建議不預選選項，未分派審查入口仍預填「請誰審」到幕僚長，使用者送出才傳訊；也可沿用既有外部審查連結。sent／relayed／recorded（已送／已轉／已記錄）分開顯示，回首頁不重置草稿、選擇或已送進度。缺來源的舊結果保留原字，明標「上次建議，現在未能確認」，不閃爍地清成空白。

## 清單統一新到舊：資料與取捨

- 這是目前事項集合的排序，不是新增全量事件歷史。去掉四種分組、By decision／By FO 及篩選；固定幕僚長入口是導覽，不進排序或件數。
- 各可處理事項用自己的 since：關卡 preparedAt，問題 ReplyFact.since／attentionAt，權限 attentionAt，審查 firstSeenAt。後備 agent.updatedAt 只能標「最後狀態更新」，不能冒稱開始等待；來源無可靠時間則「時間未知」放最後，不能用現在補值置頂。同時用 key 固定排序。
- 審查 firstSeenAt 只是本機首次看見請求，不是 GitHub 建立／更新時間；關卡 preparedAt 不是任務開工時間。這些差異直接標清來源，避免看似相同時間有不同意義。
- 完整 FO 名單仍可到達：沒有可處理事項的 FO 以狀態列顯示，同一條時間序，標明 0 件待辦，按名字開原對話；有待辦的 FO 從其事項開對話，不再另加一筆可處理事項。對 offline FO 只呈現可讀狀態，不宣稱開啟可讓它復工。名單存在不代表拉取全體歷史。
- 目前「Done」本次頁面記憶中的已記錄事項仍可回讀；在同時間序顯示 Done，不額外開完成分組；時間沿原事項來源，不因送出／記錄假造新事件。正式關閉後不新增永久歷史。主數字只數未結束事項，FO 狀態列、固定入口不重複計數。
- 未送未記錄的既有幕僚長問句留在其對話／固定入口，不再當作清單複製題；不把她自己產生的問句餵回掃描。這是本案對舊 Commander 問句列的明示取捨。
- 排名和時間序各負其責：清單永遠新在上；焦點可能指到最底的舊等待。點具名焦點直接開該件，不能為凸顯它改清單順序。保留桌面清單旁單件詳情、手機一次一頁和一鍵返回、單列狀態與原生權限去向。
- 損失：無按 FO 集合瀏覽、種類篩選和四組計數；大量新狀態可能蓋過舊待決，需要捲動。換得一種查找順序與較少模式，但不聲稱對所有查找工作更快。

## 操作數逐步重算

從幕僚長已載入、掃描完成起算；閱讀不算，點欄、輸入、Send 各 1；同一方式套用三模型，不把自動等待當零秒。桌／機如未特別說明相同。

- 知道建議：直接讀 = 0；手動掃描模型先按掃描 = 1；摘要模型需自己選點，Replay = 至少 1。
- 開推薦的正式關卡，內容已足以判斷：具名目標 1 → 選擇 1 → Confirm 1 = 3；需要開完整簡報再加 1 = 4；閱讀是否足夠由艦長判斷。
- 要求修改／暫緩：具名目標 1 → 選擇 1 → 點原因欄 1 → 連續輸入 1 → Confirm 1 = 5；需完整簡報再加 1。沒有因推薦而取消理由。
- 回答 FO 問題：開該問題對話 1 → 點欄 1 → 輸入 1 → Send 1 = 4；普通方向在幕僚長現頁為點欄 1 → 輸入 1 → Send 1 = 3。
- 權限：推薦入口開正確原生代理 1；宿主批准、回 Bridge 的次數未驗證，不能把 1 寫成權限已完成。
- 已分派審查：開既有 FO 詳情 1，傳訊再加 3；直接外部連結是開 GitHub 為止 1，實際審查工作不計為完成。未分派審查：開預填問句 1 → Send 1 = 2，編輯另計點欄和輸入，不自動傳送。
- 手動看全板：桌面已在旁為 0；手機 Board 1。找非推薦事項：桌面選列 1，手機 Board 1 + 選列 1 = 2，捲動另計。
- 找無待辦 FO：桌面狀態列 1；手機 Board 1 + 狀態列 1 = 2。舊完整名單模型是桌 2／機 3，本案沒有 By FO 切換；長清單可能增加捲動。
- 從任一 Bridge 詳情回幕僚長：固定返回 1，不經 Board。尚需重新判讀的來源可加原有重查 1，但不偷偷發模型。
- 首次需要換官：開換官確認 1 → 確認換官 1 = 額外 2；取消為開確認 1 → 取消 1，原對話維持，不納入穩態的零操作讀焦點。
