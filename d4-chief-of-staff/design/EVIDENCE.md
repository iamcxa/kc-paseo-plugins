## 什麼是事件：身份、回應與完整性

來源仍是指定產品 7a4dbc057803d791dc5626182636c8e0fc2c2d32 的 Board 與既有工具，不以模型感覺決定是否發生事件。

- 一個可加權事件是已確認的新待艦長事項，或該事項實質修訂：正式 awaiting-captain 關卡、具名權限請求、next-owner=captain 或現有 ReplyFact 確認的具名問題、向艦長提出的審查請求。類型、擁有者、事項身份、來源版本及時間必須有依據。
- 依現有事項身份去重，不憑相似標題合併不同題目。關卡以完整 workflowDir／slug／stage 為同一邏輯位置，briefingId／preparedAt 是其版本；新版替代舊版，不把同一關卡當兩件。問題使用來源訊息身份／範圍，權限使用原始請求身份，審查用完整 owner/repo/number 或 URL。相同來源版本再送、重查或重連補送不加一票。既有清單中同一事項只留目前有效版本。
- FO 忙碌、閒置、單純離線、錯誤或未確認是問題的新回覆，只是 Board 狀態，權重與門檻件數均為 0。代理自己說「重要」不能提高權重。自己的 Terra／Opus 回覆、正在分析／已分析狀態、計時更新、檢查時間及數字跳動不是新事件。
- 事件開始時間是來源可證實的新等待／修訂時間。firstSeenAt 只證明本機首次看到審查；agent.updatedAt 只證明狀態更新，不能冒稱開始等艦長。沒有可信時間不倒填成現在或五分鐘前，暫停該批自動觸發並標未知。
- 回應是艦長針對帶明確批次上下文的對話按送出，或在具名事項完成對應的既有操作。普通無關聊天、看到數字、打開頁面、草稿或滑過清單都不算回應；不因訊息相鄰就推定他回答了哪件。正式來源證明已解除／已關閉，也從待回應集合移除，不冒稱是艦長做的。
- 點開呼叫只表示已看見，可停止本次跳動，不能等同已批准或回覆。針對本批討論回應後，消耗本批，不再以相同事件重新呼叫；尚未完成的事項仍在 Board，不因此標記完成。
- 來源覆蓋不全、斷線期間事件缺口、身份／時間不可確認時不以零或新事件補值，不用這個缺口湊 X／Y。總數顯示 ?，保留現有來源重查。這是自動觸發的保守界線，不阻止艦長自己進對話或手動處理已知事項。

## 五分鐘、X、Y 與頻率：可重算的提案

先使用規則，不為每個事件花模型回合。每次有效新事件、已回應／解除及最早等待跨過五分鐘時重新算數；時鐘本身不形成新事件，也不直接發模型。

- 建議 X＝3：第一件仍待回應的有效事項之後，再有至少三件不同有效事項；同事項新版替換不增加不同事項件數。少數重複更新不該一直打擾，最低需要四件當前未回應事項。
- 重要性由可觀察種類決定：正式待艦長關卡 4；權限請求 4；具名待答問題 3；向艦長提出的審查 2；其餘狀態 0。這是提議的中斷權重，不是已證明業務收益、危害或「阻塞了四個人」。單純同 repo、同 slug 或同時出現不證明誰受阻。
- 設本批權重合計為 W；最近五分鐘至少三件不同、仍待回應的有效事項，頻率係數 F＝1.5，否則 F＝1。分數 S＝W×F。單一事項十次重送不增加頻率，狀態與來源失敗不參與。既有事件隨時間移出頻率窗會降低 F，不能沿用一個過期高頻判斷。
- 建議 Y＝8 加權分，使用嚴格 S>8，不是 S≥8，也不是要求事件數大於八。它與 X 一起決定打擾頻率：低重要、分散到達的四件審查只有八分，還不叫；同樣四件集中到達則乘 1.5，可以形成值得討論的一批。這是可解釋的起始值，未經實測校準成最佳門檻。
- 必須同時成立：最早一件仍未回應且已等至少 300 秒；其後另有至少 X 件；S>Y；必要來源可確認；沒有本批分析已啟動或尚未處理的呼叫。順序是先比對，再決定啟動，不讓 Terra 自己覆寫門檻。
- 這裡把「又收到 X」明確提議為第一件之後、同批目前仍有效的不同事項，不要求三件都發生在五分鐘到期後。門檻是整套待艦長決定的提案，不假裝他的原話已指定此解讀或分數單位。
- 全部條件通過後，先把本批身份及嘗試寫進既有幕僚長對話再分析；同批不自動重試。只維持一批在分析或等待艦長；新的事件先累積，不插話、不並發另一位幕僚長。批次處理後只用未消耗的新事件形成下一批，重新等待五分鐘。
- 五分鐘不是保證會提醒的最長時間：一個很重要的孤立關卡可能永遠未湊 X；低頻／少數請求也可能延後。沒有未經批准的高重要性例外、越過門檻的緊急通知或定期催辦。艦長仍可主動開 Bridge。

- 門檻先由規則檢查，未過門檻兩者都不跑。到了才以 GPT-6.1 Terra low 讀本批既有 Board 事實，整理事項、來源、誰明確在等、等多久、原有可走動作和未知。不要讀全部 FO 歷史、補因果、催 FO 或產生外部動作。

- 開場不再綁進入：她呼叫後，艦長回來讀「先看哪件、哪位明確在等、已知等多久、要走哪個具名動作」，接著短對話。普通進入可以沒有新話，只保留原對話。任何轉達、關卡確認及權限語義維持原樣，不由權重或模型結果自動執行。
- 若期間新事件到達，不立刻重跑；發布前用既有讀取重新確認所選事項仍待處理，說明本批與讀取時間，不聲稱已包含之後所有事件。已失效／已送或來源不可核對就不發有效呼叫，保留未知而不偷偷換目標。模型失敗同批不自動重試；下一個真正新批次仍須重新通過條件。

## 總數、紅色、跳動與音效

- 側欄總數是同一份 Board 中不同、未結束的可處理事項總和：關卡、問題、審查、權限；送出／轉交仍未正式結束者留在總數，記錄／關閉後移除，FO 純狀態與幕僚長入口不算。它不是事件件數、待艦長兩類小計或加權分數。這是本修訂對舊 sidebar-waiting 僅計關卡／問題的明示變更。
- 平時顯示普通總數，0 不額外打擾；來源不全顯示 ?。規則過門檻與模型正在整理還不變紅／播放音效，免得叫艦長回來卻沒有話。只有完成並可核對的 call-ready（已有討論焦點）才切呼叫狀態。
- 呼叫時同一數字變紅，附「幕僚長找你」的文字／無障礙名稱，短暫跳動三次後保持紅色，同批只播一次短音。這是視覺行為提案，不是本輪動態圖或實機測試；聲音不是唯一提示。點數字直接開她的對話，一次操作；看焦點後開具名目標再一次。原有關卡另選擇、原因和確認，不預選批准。
- 打開這次呼叫停止跳動，不把總數清零、不代為完成事項；針對本批真正送出回應才清除本次呼叫標示。原頁關閉／重開不重播；沒有每分鐘音效、不因每件 FO 事件發通知。

## 先查現成能力：不是一律需要新 SDK

Paseo 產品與本機 SDK（外掛開發介面）均只讀檢查，沒有呼叫、修改狀態或試播音效。公開文件以 2026-11-06 讀到的正式參考為準；llms.txt 的 Markdown 抓取先失敗，但 HTML 版參考成功讀取。安裝 SDK 版本為 0.12.0；產品工作樹仍 pinned 7a4dbc057803d791dc5626182636c8e0fc2c2d32。

- **既有 Bridge 數字。** client/sidebar-waiting.tsx 的 BoardItem 用 SidebarRow.trailing 畫 Text 徽章，按數字開 popover，summary 目前只取 waitsForCaptain 的關卡／問題。紅色及短暫跳動是這個自訂區的狀態／樣式變化，不需要改宿主才能畫數字；新總數來源要內部接回全部待辦，不能把舊小計改名冒充總和。事件監看不能只靠 Bridge 內頁掛載，否則離開就無法主動找人。
- **現成播放音效。** @getpaseo/plugin/dist/client/contracts.d.ts:105–110 有 client.playAudio({base64,mimeType})；已安裝的 app-dist 網頁 bundle 也把 createPlayAudio 接進 client context。正式[音效文件](https://paseo.sh/docs/plugins/reference#play-audio)說明可用於目前用戶端，與語音共用佇列、可能失敗或被中斷，瀏覽器需先有使用者互動；App 暫停／關閉不保證送達。故不採 window.Audio、私接系統播放器或先建新 sound API。
- **紅字與跳動。** 本機 ui.d.ts:72–88 及正式[側欄文件](https://paseo.sh/docs/plugins/reference#sidebar-items)提供 trailing 自訂內容。React Native 的文字樣式／本次顯示狀態即可做紅色和短暫視覺變化；沒有現成名為「幕僚長呼叫」的 SDK 徽章或已驗證宿主動畫策略。這是待實作的外掛 UI，不是平台必須新增的 badge API。
- **原生 attention。** protocol 的 requiresAttention 與 attentionReason 是代理快照，reason 限 finished／error／permission；agent-attention-notification.js 會組通知內容。已安裝 app.asar 中 agent-attention-policy.js 依用戶端活動／是否正在看該代理決定 shouldNotify 與 push；websocket-server 的 broadcastAgentAttention、網頁 bundle 的 shouldNotify 分支及 desktop notifications.js 形成通知路徑。Electron 的通知 silent 取決於使用者原有 notifications.playSound。這證明已有原生代理提示與音效機制，不能推論它會自動畫 Bridge 總數紅色跳動，或正好服從本案 X／Y。
- **不能任意設定原生 attention。** 本機 client 的 PaseoAgentHandle 只有讀快照，daemon-client.updateAgent 只接受 name／labels；公開 update_agent 工具另能改執行設定，但沒有 requiresAttention／自訂 attentionReason。沒有把「狀態可讀」誤寫成「可以設一個自訂 call-ready」。也不偽造 permission、finished、error 來催艦長。
- **尚需宿主確認／可能補能力。** Terra 與 Opus 的原生完工通知可能在自訂呼叫之外另響；現有公開介面未證明能對這兩個內部回合靜音／把原生完成通知合併成一次受控呼叫。send_agent_prompt 的 notifyOnFinish=false 只關完成回報，不當作作業系統靜音的證據。若宿主不能做到，就需要受支援的選擇性通知／抑制能力，由艦長決定後才進產品案；不修改全域通知設定去掩蓋問題。
- **需另決的範圍。** 指定單一仍執行且連線的用戶端可用現成 client.playAudio，加自訂紅色數字；跨多裝置只響一次、App 關閉／暫停仍送達、自訂 attention 與持久事件恢復，不是此次已證明能力。原生有 push 不代表外掛已有自訂批次 push 介面。若艦長需要這些，按任務停止條件先回他；本輪沒有新增 host capability 或啟用背景任務。

## 相同批次不重跑：仍放在她自己的對話

- 門檻前的事件緩衝由一個正在執行的觀察者維持；它是訂閱與一個最早五分鐘到期檢查，不逐件發模型、也不從頁面進入啟動。不同用戶端都看到總數，不代表各自可獨立跑一批。此提案先限一個指定用戶端，沒有宣稱分散鎖或多裝置 exactly-once。
- 達門檻後，既有幕僚長自動請求帶入 batchId（本批身份）、Board 版本、事件身份／版本／時間／權重、首次等待時間、X／Y／頻率規格及嘗試識別；她自己的完成訊息攜回相同身份、來源時間與結果。通知嘗試及已看見／已回應的本批標記也沿用這段既有對話，不設新的檔案／資料表／daemon 永久快取。這仍是既有時間線中的本案文字／資料契約，產品尚未提供。
- 重開先只讀自己時間線的最新嘗試及配對結果，與目前 Board 版本及未消耗事件比對；同批成功、失敗、未完成或已通知都不再叫模型或重播。自己的模型輸出／attention 不可重新納入 Board 事件，避免自激。重開頁面不重新起五分鐘或把原有每列都數成新到達。
- shared/timeline.ts 的 projected 讀取會保留文字、agent／epoch／序列來源範圍並排除 gap／reset／staleCursor；commanderReplies 保留完整 item.text，但目前只辨識 Collect now 的 provenance。未來需在同一讀取層辨識新的批次請求／結果／通知標記，不能宣稱舊 collection 分類已實現此機制。
- 尾端 120 筆之外要沿 before 游標讀回最新必要配對，不能從 co-chat 可見 30 行判沒有紀錄；尚未寫完、識別缺失、不同版本／來源不符或歷史不可讀都標無法確認，不自動重跑。字面標記不提供任何新增授權，引用／代理 envelope 不當作艦長回應或原生發布者證明。
- 程序重啟後，門檻前尚未寫成分析請求的記憶緩衝可能已丟失；既有 Board 快照不足以重建所有中途變化、頻率或移除事件。讀回已處理批次後，只建立新的已確認基線，再計之後真正觀察到的新事件；缺口不補觸發。不暗中加完整事件日誌；若需要保證跨程序累積不中斷，那是新的持久狀態／恢復義務，另請艦長決定。
- 播音只能在同批未曾嘗試且已 ready 的指定用戶端做一次；先記嘗試再播可抑制重開重播，但失敗或程序中斷可能沒有聲音。音效受拒時保留紅字及「音效未能播放」，可由使用者明確按播放，不自動重試。不宣稱資料與音效能原子交付或背景一定送達。
