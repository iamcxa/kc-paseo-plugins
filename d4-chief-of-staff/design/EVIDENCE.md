## 先比較互動模型，再選方向

起點一致：幕僚長頁面已載入，使用者尚未操作，沒有換官提示；桌面／手機相同。一次點按、一次點欄、一次連續輸入、一次送出各算 1；閱讀及等待不算，捲動另計。時間與理解品質未量測。

1. 自動開場對話：進入即檢查，改變才掃描；知道建議 0，開具名目標 1。理解後的決策仍走原確認流程。
2. 手動掃描對話：按掃描 1，再開目標 1；相同可見結果多 1，且要先知道得按掃描。優點是使用者控制每次模型回合，缺點是不符進入即對齊焦點。
3. 摘要加 Replay：以已完成摘要起算讀摘要 0，Replay 1，再開 FO 1；若從尚未收集開始還需 collect now 1。摘要本身沒替艦長挑出唯一下一步。保留多點背景，但多一層理解與挑選。

選 1：少一個啟動動作，沒有新增模式，維持既有對話。選擇理由是任務的進入情境和操作數，不宣稱已證明更快。重進未變時不增加模型回合；不是一進入就無條件喚起模型。

## 排名規則與不能推論的事

1. 候選必須是未結束、未送出／轉交，且其必要來源已可確認的目前事項。權限只開具名原生會話，關卡只開具名關卡，問題開正確 FO 對話，審查保留現有去向與外部連結。來源失敗的候選不能當作已確認。
2. 第一層是已可確定某位 FO 在等艦長：權限記錄指到該代理，完整 workflowDir + slug 的正式待艦長關卡，或 next-owner=captain 的具名下一步／現有問句判定。只說「這件正等你」，不保證批准後就開工。不同層的規則是建議預設，沒有替來源增加業務重要性。
3. 第二層是 GitHub 明確向艦長發出的審查請求，但沒有可確認的 FO 等待歸屬。可說「審查請求等你；尚不能確認誰受阻」。同儲存庫、時間相近或同名任務都不足以宣稱誰被擋住。
4. 同層用事項 since 的較早有效時間先（久等先）；時間不明者後，再以完整事項 key 的固定字序決勝。沒有依據的人數、收益、工時、緊急性或跨任務依賴不參與排名。
5. FO 只是 busy／idle／new reply／error／offline 不入候選；新回覆必須已有清單問句判定，不能從狀態升級成「等艦長」。同一 FO 的關卡和另一題不能合併；同一關卡不能因關聯兩列就加兩票。
6. 目前 attachGates 會在精確匹配失敗後用同 slug 或 workflow 後備關聯；reviewOwner 會用同 repo 或文字找第一位 FO。這可作現有導覽，不是無推論的歸屬證據。排名只接受唯一的完整 workflow/task 關卡歸屬、權限原始 agentId、明確且唯一的問題來源；審查若只有 repo 對上，就顯示「相關 FO，等待歸屬未知」，不擴大成第一層或多人解阻。
7. 資料有缺口時可推薦「已確認事項中，先看這件」，同時指出缺哪個來源；全不可確認便不選，說「現在不能判定」。不能把空集合當作全艦隊無事，也不能因 source retry 失敗再次發模型回合。

這不是求證實際依賴的計畫系統。她只把「你可以做、有人明確在等」排在「只有請求、影響未知」之前；沒有聲稱全局最佳。

## 進入、版本比較、成本上限的精確意思（第二版）

- 進入指首次掛載、全頁重開及 Board／詳情返回對話的 inactive→active；重開也先比對，不能因記憶消失另付一次掃描。既有 client/board.tsx 的 open 與 client/co-chat.tsx 的 visible 可供內部返回；宿主未卸載元件時的 App／分頁回前景訊號仍未驗證，若需新 Paseo 能力就回艦長。
- 比較身份先放在已存在的對話，不採另一個永久快取：最近一次完整掃描的 assistant_message（幕僚長回覆）攜帶 Board 版本、掃描識別、讀取時間與單件建議；對應的既有自動 user_message（掃描請求）也攜帶相同版本與識別。都是原有對話訊息，不新增檔案、資料庫、標籤儲存或伺服器 rounds 記憶體依賴；本次記憶只加速讀回，不是去重的權威來源。
- Board 版本是同一規格正規化事實的 SHA-256（內容指紋），不由模型隨意填寫；Bridge 送出時給定，回覆須原樣帶回。內容仍含 FO 成員／實質狀態、next-owner／next／task／workflow、問題來源及時間、權限身份內容、完整關卡身份、審查身份內容／firstSeenAt，以及可核實的送達／記錄狀態。規格識別也要可辨；不同規格只能說無法比較，不算 Board 改變。
- 排除 roundId、collectedAt、checkedAt、相對時間、物件順序、無關的 agent.updatedAt 及幕僚長自己的輸出／工作狀態。讀取過程的 loading、來源暫時失敗或恢復只改完整性標示，不能單獨證明事項改了；恢復後比對內容，仍相同就不掃。缺必要欄位不能補空值後當作新版本。
- 開場讀取順序是：取得目前可核實的 Board 事實 → 只讀幕僚長自己的既有投影時間線，找最新掃描嘗試與配對回覆 → 比較版本。最近嘗試成功且版本相同，直接顯示原單件建議，附原讀取時間及本次檢查時間；沒有模型回合，也不補發一句「沒有變化」。這適用全頁重開，不以本次記憶仍在為條件。
- 最近自動請求版本相同、但沒有可確認的完整成功回覆，則保留「掃描尚未完成／未能確認」或原舊建議，不發第二次。它保護了模型失敗、回覆缺識別、重開發生於掃描途中等情況；不能跳過最近失敗嘗試、只找更早成功回覆後重試。只有讀完整個可確認歷史、沒有任何掃描請求／回覆時，才能認定未曾掃描並做第一次；沒有記憶不等於沒有紀錄。
- 必要來源齊全並確定版本不同，下一次有效進入最多啟動一個掃描模型回合。本次鎖仍避免同頁同時發送；代理忙碌就不插隊、不排忙完自動掃。掃描期間 Board 變更，結果標原讀取時間及之後已有變更，不立即重掃。此次只界定重新開頁後的去重，不新增跨多個同時開啟客戶端的分散鎖。
- 全頁重開可能丟失本次送達進度；先用既有正式來源／對話中的原決定紀錄核對。若僅是本次記憶消失、無法還原，列為未知，不轉成「未送出」，不拿它製造版本不同；對可能已送的目標不再建議重做。這不宣稱新保存或跨次恢復草稿，亦不改第九輪的本次進度語義。
- 沒有候選且來源完整時直接說目前沒有可確認待辦，不啟動模型；全缺來源也不啟動。時間線讀取失敗、斷頁、截斷、身份不符或無法比較時，保留可讀舊內容並標「上次建議，現在未能確認」；資料重查只重讀，不發模型。使用者仍可自行在對話追問，不把正常追問算成自動重掃。
- 一回合可能多次供應商請求；未變的重進／重開為 0 個新增掃描回合，改變後最多 1，無自動重試或背景掃描。讀自己的時間線有額外讀取量，未量測；這不是模型零成本以外的零延遲保證，也不是 token 或金額硬上限。

### 為何投影時間線可承載掃描身份，及現行接線的缺口

第一考慮是派工指定的「上次掃描訊息」，而不是新增儲存。以下均為既有 pinned 產品 7a4dbc057803d791dc5626182636c8e0fc2c2d32 的讀碼證據，未改或執行產品：

- shared/timeline.ts:1–30 的 readTimeline 固定 projected（投影後訊息），保留每筆文字、agentId、epoch、seqStart／seqEnd 及 sourceSeqRanges；healthyTimeline 排除 reset、staleCursor、gap、error、錯誤代理／epoch，並限制每頁最多 120 筆。投影不是只能讀顯示摘要，因此可以讀出訊息中的版本；entryIsWriting 排除尚在寫的尾端 assistant entry，不能拿半段回覆作成功身份。
- shared/commander-replies.ts:11–26 的 commanderReplies 保留完整 item.text 和來源範圍，不要求 seqStart 等於 seqEnd；projected-timeline.test.mts 既有案例也描述合併文字及跨顯示列游標。但它目前只識別 Collect now，其他自動請求可能沿用 unknown／前個 provenance；**不能直接拿現有 collection 分類當幕僚長掃描已接好**。未來需在既有讀取層辨識這種掃描請求與回覆的配對，這是 Bridge 內部文字契約，不是新的 Paseo API 或新儲存。
- client/co-chat.tsx:257–276 只拉尾端 120 筆；shared/chat-lines.ts 的 toLines 最後還只留 30 個可見對話行。因此不能從目前畫面或單一尾頁推斷「沒有上次掃描」。辨識在 toLines 裁切及 Markdown 顯示之前做，取原投影文字；對同一回覆被合併／拆為多個 display entries 的情形，保留完整來源範圍，遇到未收齊的識別不當作不存在。
- 先讀 tail，再以最早一筆 seqStart 和同 epoch 向 before（更早頁）讀，每頁上限沿用 120；找到最新一次掃描嘗試及其匹配回覆即可停。不在第一頁就繼續只讀自己的歷史，不讀 FO 歷史、不啟動模型。若任何頁 hasOlder 仍為真而尚未讀到需要的前文，屬「還沒找到」，不是「從未掃描」；只有乾淨讀到歷史起點才能作首次判斷。失敗／無進展游標／超時則停，標未知，不付模型去填補。
- 配對檢查使用目前 host、幕僚長 agentId、同 epoch、請求與回覆的完整 seq 範圍、相同掃描識別與 Board 版本，並核對獨立自動請求以及其後完整回覆，中間沒有另一個新的請求或使用者回合。內文引用、代理 envelope 及 FO 回報中長得像識別的字串不能用子字串匹配成掃描紀錄。既有自動標記本身不是已驗證的發送者證明；若使用者貼入的完整範例與實際自動請求無法區分，標未知並抑制自動掃描，不宣稱找到可信成功紀錄。訊息文字不是額外授權，更不能觸發傳令。
- 回覆中缺版本或與請求不符，不「修補」它；請求本身足以證明這版本已嘗試，故保持未知且不自動重掃。成功訊息提供可重用焦點，請求提供失敗／未完的抑制；不靠已移除的摘要 rounds Map，重開 Bridge／伺服器記憶消失也不重置此依據。

判斷：現有投影讀取能保存並分頁讀到所需文字和身份，所以此方向可用既有對話承載；**現有產品尚無該訊息契約／配對解析，不能宣稱已運作**。若實作證明投影會不可逆地刪去該紀錄、不能辨識來源或不能完整分頁，先停；最小備案是在既有 coordinator-switch 記錄加入「最後掃描版本＋原訊息引用」兩個欄位。那仍是新持久狀態，必須由艦長另行決定，不在本輪採用，亦不回退成重開就首掃。
