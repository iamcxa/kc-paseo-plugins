Spacedock Bridge is a screen and a panel for running a fleet of Spacedock first officers (FOs) from Paseo. The Bridge opens on Commander, the existing comms officer conversation. Desktop keeps a 330 px board beside the wide detail; phone opens on the conversation and uses Board to reach the list. The Fleet panel lists every FO agent with its task and stage.

The Bridge sidebar shows gates and questions still waiting on you, even before you open Bridge. Its separate count button opens a desktop popover or a compact bottom sheet, with gate and question counts and the newest items first, each labelled by owner and age. An item opens its Bridge detail; Open Bridge opens the board. Pressing the Bridge label opens Bridge as before. Sent or relayed gates do not count here. A loading or failed source shows ? and an incomplete-list note rather than zero; Check again retries the existing readers. These reads use the existing FO and Commander subscriptions and the gate/decision readers at the existing one-minute interval; the sidebar does not create a comms officer.

The plugin creates one comms officer agent. It starts FOs or passes work and rulings only when the Captain asks. For collection it reads existing reports only and treats missing reports as unknown; it never asks an FO for a report. It does not read repositories or answer permission prompts. A local fleet MCP server gives it a `fleet_status` tool that lists FOs, their tasks and the gates waiting on you.

Use 立即收集 in Commander to collect one bounded snapshot and request one structured digest. There is no digest schedule or background collection. Each FO contributes at most 40 projected display entries and 64,000 bytes of assistant report text. Reports are admitted newest-first, charging only admitted UTF-8 bytes, then returned in timeline order; truncated or failed reads are explicit. One shared reader validates the host’s projected timelines, preserves each complete display entry and its source ranges/collapse markers, and classifies the preceding request. Healthy empty pages are readable; identity, epoch, reset, gap, stale-cursor and page bounds remain checked. Collection replies stay subject to validation across agent messages and automated notifications; an actual Captain request resumes ordinary discussion, including Markdown and JSON examples. Only known ordinary discussion enters question previews and counts, including the sidebar while Bridge is closed. Unknown provenance fails closed. A digest is one projected display entry over its full declared sequence range and merged text; it is never assembled from separate display entries. Exact reads are bounded to 120 display entries, independently of how many underlying sequences each spans, and Replay verifies that same entry. Exact-start reads include sequence zero without an invalid negative cursor. Previous-officer history uses the same guarded reader; missing identity shows unavailable. Every point and each of its three context lines must use exact source objects from that collection. Bridge reads the assistant messages back by host, agent, epoch and sequence, then checks the SHA-256 hash of the complete merged text before showing the digest. A currently streaming latest assistant entry, or a changed range/text, is unavailable until it can be verified. Invalid or unavailable data shows 摘要無法驗證; raw JSON is never a fallback. Hashes establish source identity, not the truth of a paraphrase or its claimed cause.

Replay shows the point's three sourced context lines and the quoted message within its own FO conversation, initially two projected display entries on each side. Its source links select their own exact messages. Earlier/later expand from the window edges; source loss, missing sides and exhausted history have distinct messages. Open FO opens the exact source officer in Bridge’s existing conversation-only detail on the current source host, with ← Commander and both unsent drafts retained. An unavailable host or officer stays explicit instead of substituting another conversation. Replay keeps the selected point and actions outside its scrolling history; if its context cannot currently be checked, a leading warning names the requested original and the three context lines and old window are withheld. A whole-request failure uses that state for earlier/later loads too; retry keeps the warning until a verified result returns. A successfully revalidated window with an unavailable neighboring side retains its verified context. An unfinished neighbour is withheld and its side stays unavailable and retryable. Open digest and Replay readers re-verify on Commander and round FO lifecycle changes, including completion with unchanged content. Subscription failures hide unverified content until an explicit retry reconnects; collection membership stays pinned to the original round. Continue discussing and reply with a new decision both return to the Commander composer, retain the existing draft and add removable point context. They never send, choose a gate or make a gate decision. An explicit send keeps the quoted point separate from the Captain's text.

An existing officer keeps its original instructions until you confirm 換用新的通訊官. Only confirmation creates the officer with the new prompt and archives the old officer. 讀取舊通訊官對話 opens its retained timeline read-only. The switch remembers only the old and replacement officer IDs. Collection rounds and source membership stay in memory, bounded to the latest 24 rounds; a server restart or expired round makes old digests unverifiable, with no inferred replacement. Digest usage has not been measured: an integrated isolated measurement needs a separately approved configurable fleet listener and data directory.

The ↑ label names the message's recipient. Decision buttons to its left open a separate reason field with Confirm and Cancel; only Confirm sends the decision through the comms officer. Approve allows an empty reason; revise and hold require one. The message is never copied into the reason. Each action keeps the other draft, and Cancel keeps the reason. Discussion is labelled with its officer and includes other tasks.

Unsent message and reason drafts stay separately in memory per agent and gate while switching items, returning to Commander or reopening the board. Edits and clears appear in every open composer for that target. A successful send or decision clears its own submitted draft only if it has not changed; a refusal keeps it. A changed briefing requires choosing the decision again. Asking the comms officer keeps any existing message draft. Drafts are lost on plugin or app reload.

While a reply is sending, its ↑ and Enter stay disabled even after reopening that target. A failed send keeps the draft and enables sending again.

Both list views and their counts show loading or an incomplete-list message until FOs, gates, reviews and the comms officer have been checked. The By FO view shows no-agents text only for a checked empty list. FO checks include reading their unread questions; a failed question read keeps the list incomplete. A failed workflow names its directory while other workflows' gates and tasks stay visible. The desktop board pins Commander above its filters; a waiting question and its age appear on that card, with no duplicate question row. The compact board shows that question once in Questions. A Commander question counts once; the general conversation entry never adds a pending item. Detection reads the last displayed assistant message. Sent and relayed decisions remain pending with a single waiting marker; recorded or no-longer-open items leave the pending counts. Items recorded in this session remain reachable under Done this session at the end of the board, outside every count and kind filter, reopening to their result and reason without decision controls. One shared gate identity scopes ownership matching, message/reason drafts, choices, sending locks, completion and retained details to the source workflow, task, stage and briefing identifier. An officer matching both workflow and task is preferred before the existing ownership fallbacks; each composer also keeps its recipient namespace. A later stage or another attempt stays pending independently of an earlier result. Previously opened details remain mounted for this session, retaining their choice, reason and progress, while hidden details reject stale actions. Reopening a closed gate shows its recorded decision, or a neutral no-longer-open message if none was recorded. Closed or recorded gate cards hide the decision controls and waiting age while keeping ordinary FO discussion. An older briefing's resolution does not mark a newer briefing as recorded. A claimed decision keeps its progress visible and does not offer a second submission. Returning from a card that showed a record refreshes gates once.

Every review row shows its repository and pull request number in the main content, in both list views. Long repository names truncate while the number stays visible; a separate icon opens GitHub.

Queue titles occupy their own line and wrap to two lines, with the FO name, item kind, tab badge and age underneath. The neutral Board headline counts all pending items, including ones waiting on someone else. By FO lists every known FO, including those with no waiting items; its count is officers, and each officer shows its own pending-item count and opens only its conversation, without a question label, waiting age or briefing controls. Kind filters apply only to By decision, retaining the previous filter when switching back. Comms questions show the displayed reply's timestamp age, or unknown when no timestamp is available. Comms and FO questions stay separately attributed; matching wording is not proof of a shared request. FO question details use the officer plus the question message or timestamp and title, so a later question keeps its own title and age. Discussion drafts retain their existing recipient scope across question details.

Retained details keep the officer, recipient and source captured when opened. Gate reads and validation use that attempt's source workflow, even if its officer moves to a different workflow. Every reactivation refreshes briefing, decision-record, delivery-status, gate state and conversation data under the captured identity, even after a successful read. Failed or unresolved readers also offer a retry control without clearing drafts. An authoritative null clears a released claim and its cached sent/relay progress. Reads that overlap a newer local submission cannot replace that submission, while recorded decisions remain terminal. Conversation subscription failures reconnect through the same retry. Commander question and connection retries keep the first connected recipient. Each reader ignores superseded results and keeps its own failure until its own successful read. Once an open briefing loads, polling follows subsequent closure or recording. Returning to the phone board refreshes all live sources; those readers follow the current fleet, independently of retained detail identities. A failed FO, gate, task or comms source offers Check again through its existing reader. Review source retry reads the poller's stored result; its next automatic GitHub check remains scheduled by the poller.

On compact screens, Hide briefing ▴ reduces the decision card's briefing to one question line; Show briefing ▾ restores it. A fixed ← Commander returns from every Bridge drill-down, including the compact Board, in one step. ← Queue returns to the retained list position to choose another item. Commander keeps its draft and conversation scroll position across these detours. These presentation choices use only the current mounted session, with no added storage or history. The card's ← Queue control, delivery feedback and errors stay visible in both states. Feedback shows one status line and at most two content lines; More appears when text is clipped and opens the full text. On compact native clients the briefing temporarily collapses while the keyboard is open, then restores the user's previous choice when it closes; Show briefing dismisses the keyboard first. The chat leaves room for the keyboard. The message and decision reason share a shrinkable scroll area, so their controls remain reachable when both drafts are long. Android compact screens also get an approximate 20 dp bottom margin while the keyboard is closed; the host exposes no exact navigation-bar inset.

Setup: Paseo 0.12.0 or later, and the `spacedock` command on your PATH. FOs are agents labelled `role=fo`. Task and gate data come from running `spacedock` against each FO's workflow directory.

A neutral Tab closed badge beside an FO's name means it has known Paseo tab labels, all are false, and it is not running. It stays visible when opening a decision card. Missing tab labels or any open client tab leave it unbadged. The badge preserves the FO's group and actions; archived or lifecycle-closed agents keep the existing offline behavior.

What it keeps and sends: decisions, review requests, a fleet token and the old/replacement officer IDs are stored under `~/.local/share/paseo-fo-coordinator`. The fleet MCP server listens on `127.0.0.1:6787`, so a second copy of the plugin on the same machine cannot start it. A review poller runs inside the daemon and wakes the FO that a pull request belongs to.
