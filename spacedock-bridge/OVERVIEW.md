Spacedock Bridge is a screen and a panel for running a fleet of Spacedock first officers (FOs) from Paseo. The Bridge screen shows decisions waiting on you, review requests and a chat with a comms officer agent. The Fleet panel lists every FO agent with its task and stage.

The plugin creates one comms officer agent. It only starts FOs and passes messages. It does not read repositories or answer permission prompts. A local fleet MCP server gives it a `fleet_status` tool that lists FOs, their tasks and the gates waiting on you.

The ↑ label names the reply's recipient; decision buttons send through the comms officer. Unsent drafts stay in memory per agent and gate while switching items or compact tabs. Edits and clears appear in every open composer for that target. A successful send or decision clears its submitted draft only if it has not changed; a refusal keeps it. Asking the comms officer keeps any existing draft. Drafts are lost on plugin or app reload.

While a reply is sending, its ↑ and Enter stay disabled even after reopening that target. A failed send keeps the draft and enables sending again.

Both list views and their counts show loading or an incomplete-list message until FOs, gates, reviews and the comms officer have been checked. The By FO view shows no-agents text only for a checked empty list. FO checks include reading their unread questions; a failed question read keeps the list incomplete. A failed workflow names its directory while other workflows' gates and tasks stay visible. Comms-officer questions appear on the compact FOs tab without opening the chat; detection reads the last displayed assistant message. Reopening a closed gate shows its recorded decision, or a neutral no-longer-open message if none was recorded. Closed or recorded gate cards hide the decision controls and waiting age while keeping ordinary FO discussion. An older briefing's resolution leaves a newer open briefing's decision controls available. Returning from a card that showed a record refreshes gates once.

Queue titles occupy their own line and wrap to two lines, with the FO name, item kind, tab badge and age underneath. By FO uses the same individual item rows and destinations, and its waiting count equals those rows. Comms questions show the displayed reply's timestamp age, or unknown when no timestamp is available. Comms and FO questions stay separately attributed; matching wording is not proof of a shared request.

A failed FO, gate, task or comms source offers Check again through its existing reader. A pending read replaces the retry control, and a newer read supersedes an older response. Review reads return stored results, so a failed review source shows the poller's next scheduled automatic check (or unknown), with no immediate GitHub retry control.

On compact screens, Hide briefing ▴ reduces the decision card's briefing to one question line; Show briefing ▾ restores it. The card's ← Queue control, delivery feedback and errors stay visible in both states. Feedback shows one status line and at most two content lines; More appears when text is clipped and opens the full text. On compact native clients the briefing temporarily collapses while the keyboard is open, then restores the user's previous choice when it closes; Show briefing dismisses the keyboard first. The chat leaves room for the keyboard. Android compact screens also get an approximate 20 dp bottom margin while the keyboard is closed; the host exposes no exact navigation-bar inset.

Setup: Paseo 0.12.0 or later, and the `spacedock` command on your PATH. FOs are agents labelled `role=fo`. Task and gate data come from running `spacedock` against each FO's workflow directory.

A neutral Tab closed badge beside an FO's name means it has known Paseo tab labels, all are false, and it is not running. It stays visible when opening a decision card. Missing tab labels or any open client tab leave it unbadged. The badge preserves the FO's group and actions; archived or lifecycle-closed agents keep the existing offline behavior.

What it keeps and sends: decisions, review requests and a fleet token are stored under `~/.local/share/paseo-fo-coordinator`. The fleet MCP server listens on `127.0.0.1:6787`, so a second copy of the plugin on the same machine cannot start it. A review poller runs inside the daemon and wakes the FO that a pull request belongs to.
